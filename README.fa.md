# CrashVault — وقتی پاسخ موفقیت می‌دهی، داده باید پشتش باشد

یک موتور ذخیره‌سازی کوچک با دو پیاده‌سازی مستقل در **Python و C11**. عملیات روی یک لاگ باینری ثبت می‌شوند و بعد از راه‌اندازی مجدد، وضعیت کلیدها از همان فایل بازسازی می‌شود.

![معماری ثبت و بازیابی](assets/architecture.svg)

مسئلهٔ اصلی فقط ذخیره کردن نیست: اگر نوشتن وسط کار قطع شود، کدام عملیات معتبرند؟ رکورد ناقص انتهای فایل حذف می‌شود؛ خرابی رکورد کامل باید خطا بدهد. هر دو زبان قالب یکسانی دارند و فایل همدیگر را می‌خوانند.

## اجرا در PowerShell

```powershell
New-Item -ItemType Directory -Force build | Out-Null
gcc -std=c11 -O2 -Wall -Wextra -Wpedantic c/crashvault.c -o build/crashvault.exe
"PUT`tuser:42`tAda", "GET`tuser:42" | python python/crashvault.py demo.log
"GET`tuser:42", "STATS" | ./build/crashvault.exe demo.log
python -m unittest discover -s tests -v
```

برای لینوکس و جزئیات API، [راهنمای انگلیسی](README.md) را ببینید. کلیدها و مقادیر فقط ASCII قابل چاپ‌اند؛ کلید حداکثر ۱۰۲۴ و مقدار حداکثر ۶۵٬۵۳۶ بایت است. هم‌زمان فقط یک پردازش یا یک Store باید فایل را باز کند؛ قفل چندپردازشی پیاده‌سازی نشده است.

## شواهد کیفیت

- ۲۰۰۰ عملیات تصادفی با بذر ثابت، مقایسه با مرجع و تطابق دقیق بایت‌های فایل در هر دو زبان.
- بررسی همهٔ نقاط قطع بایتی یک تاریخچهٔ چندرکوردی.
- بررسی همهٔ تغییرات تک‌بیتی یک فایل کوچک و رد کردن فایل خراب.
- کشتن واقعی پردازش بعد از دریافت پاسخ موفق و بازیابی مقدار ثبت‌شده.
- بررسی برخورد هش، حذف کلیدها، ورودی نامعتبر و اندازه‌های مرزی.

حالت پیش‌فرض قبل از پاسخ موفق، درخواست sync فایل می‌دهد. تست‌ها قطع پردازش و کوتاه شدن مصنوعی فایل را بررسی می‌کنند، نه قطع برق واقعی. پوشهٔ والد هنگام ایجاد فایل sync نمی‌شود. حالت `--no-sync` این تضمین را ضعیف می‌کند و فقط برای آزمایش جداگانه در نظر گرفته شده است.
